# Demo repositories

Two small but realistic repositories with a scripted history, built so every
RepoMind feature has something real to find. They are generated by
`build_demo_repos.py`, so they can be rebuilt identically at any time.

| | **ShopWise** (`shopwise/`) | **TaskFlow** (`taskflow/`) |
|---|---|---|
| Stack | Python, FastAPI, SQLAlchemy | TypeScript, Express, Prisma |
| History | 23 commits, 3 developers, Jan–May 2026 | 16 commits, 3 developers, Jan–May 2026 |
| Decisions to reconstruct | pydantic validation; raw sqlite3 → SQLAlchemy (+ Postgres); Redis catalog cache; payment gateway adapter; structlog | JavaScript → TypeScript (a 10-file rename); callbacks → async/await classes; `pg` replaced by Prisma; zod; `@app/*` alias + barrels; domain event bus |
| Drift story (health chart) | 100 → 92.6 (sales-report hotfix reads the order repository) → 100 (moved into ReportService) → 93.7 (stock endpoint) → 89.0 (admin listing) | 100 → 95.5 (archive hotfix writes through Prisma) → 100 (moved into TaskService) → 92.7 (project page counts tasks via an injected TaskRepository) |
| Violations at HEAD | `routers/products.py` and `routers/users.py` call and import repositories | `project.controller.ts` calls `TaskRepository.countOpenByProject` (found through the `@app` alias, the barrel and the injected field) |

`tests/test_demo_repos.py` checks this story on every test run.

## One-time setup

1. Build them (outside this repository, in `../repomind-demos`):
   ```
   python demo/build_demo_repos.py build
   ```
2. On GitHub, create two **empty** public repositories, e.g. `repomind-demo-shopwise` and
   `repomind-demo-taskflow` (no README, no licence).
3. Push each one:
   ```
   cd ../repomind-demos/shopwise
   git remote add origin https://github.com/<you>/repomind-demo-shopwise.git
   git push -u origin main
   ```
   (same for `taskflow`).
4. A fine-grained token for raising issues from the app: GitHub → Settings → Developer settings →
   Fine-grained tokens → only these two repositories → **Issues: Read and write**. Put it in
   RepoMind's `.env` as `GITHUB_TOKEN=...` and restart the server. The same token lifts the GitHub
   API limit used to check repositories before cloning.
5. For the automatic review on every push, in **each** demo repository: Settings → Secrets and
   variables → Actions → add `BEDROCK_API_KEY` and `BEDROCK_REGION`. Then:
   ```
   python demo/build_demo_repos.py ci ../repomind-demos/shopwise
   cd ../repomind-demos/shopwise && git push
   ```
   That push only adds the workflow, so its own review finds nothing. Do this before demo day and
   check the **Actions** tab shows a green run. The workflow checks out RepoMind from
   `Sriram-Kommmana/repoMindAI`: that repository must be public, or add a `REPOMIND_CHECKOUT_TOKEN`
   secret and uncomment the `token:` line in the workflow.

## Demo-day walkthrough (about 8 minutes)

Start RepoMind (`python server.py`), open http://localhost:8000.

1. **Analyze** `https://github.com/<you>/repomind-demo-shopwise`. Point at the live progress line
   (clone, parse, graph, history snapshots) — about 15 seconds.
2. **Overview and diagram**: 37 files, the layered structure (routers → services → repositories,
   adapters, core).
3. **Architecture drift**: two rules broken, health 89. Open a group: the AI explanation names the
   exact routers and functions and how to fix them.
4. **History**: the health chart — the March hotfix, the fix a week later back to 100, the drift
   that came back. Click a point to see the architecture at that commit.
5. **Decisions (ADRs)**: the switch from raw sqlite3 to SQLAlchemy, reconstructed from the commit
   history with the evidence commits and a confidence level (titles are written by the AI and vary
   a little between runs).
6. **Ask**: "Which routers talk to the database directly, and how should they be fixed?" — the answer
   cites the files and functions it looked at.
7. Switch to **TaskFlow** to show the same on TypeScript: the pg → Prisma replacement decision, the
   JS → TS migration, and the violation found through a path alias and an injected field.

### The live code review (the closing moment)

1. In a terminal:
   ```
   python demo/build_demo_repos.py bad ../repomind-demos/shopwise
   cd ../repomind-demos/shopwise && git push
   ```
   The commit adds an order search with SQL injection that also reaches the database from a router,
   a hard-coded payment secret, a division by zero, and a swallowed exception.
2. Open the repository's **Actions** tab: the RepoMind review runs (2–3 minutes, mostly installing
   RepoMind), then the
   **Issues** tab fills with one issue per problem, labelled `repomind-review`, each linking to the
   exact line.
3. Back in the app, re-analyze and open **Code Review** → *Review the last 1 commit* to show the same
   findings, already marked "already open #n".
4. Push the fix:
   ```
   python demo/build_demo_repos.py fix ../repomind-demos/shopwise
   git push
   ```
   RepoMind closes the issues whose problem is gone, with a comment.

TaskFlow has its own `bad` / `fix` pair (a missing `await`, an assignment inside an `if`, raw SQL
built from a query parameter in a controller).

### What to expect from the AI

Measured on 6 rehearsals of each bad commit: every planted problem was found every time. Reviews of
the fix commits came back clean in most runs; the AI can still raise an occasional medium finding on
the fix — it is reviewing new code, and some of those findings were real enough that the fix code
here was improved because of them. Findings below medium severity are never filed as issues.

## Resetting after a rehearsal

```
python demo/build_demo_repos.py build
cd ../repomind-demos/shopwise && git push --force origin main
```
Rebuilding recreates the exact same history (same commit hashes), so force-pushing restores the
starting point. Close or delete any issues left from the rehearsal on GitHub first: RepoMind never
re-raises a finding whose issue was closed, so leftover closed issues would hide findings in the
next run.

## Fallbacks

- **Slow network**: the repositories are about 250 KB each, so cloning is never the slow part; have
  both analyzed once before presenting anyway.
- **Model hiccup**: every AI section degrades to its deterministic part (violations, health, history,
  detected decisions) and says so; re-running a section uses the cache for whatever already succeeded.
